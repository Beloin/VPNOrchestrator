# SDN + VPN + Orchestration — Project Notes

A local project to learn **orchestration**, the **control/data-plane split**, and a real
network function (a small VPN), using [Click](https://github.com/kohler/click) as the data
plane and Python for the control and management planes.

## Goal

- Focus: **orchestration** and the **control plane**, without hiding the data plane.
- Data plane may be low-level, but it is not a black box: Click's config is a readable
  element graph, so you can see exactly what the forwarding does.
- Deliverable: a working, non-toy VPN with a clean three-plane separation.

## The three planes

| Plane | Job | Concrete example (VPN) |
|---|---|---|
| **Data plane** | forwards packets, fast and dumb | Click encapsulates / forwards |
| **Control plane** | decides routes, keys, tunnels at runtime | key exchange, route exchange, keepalive |
| **Management plane** | config, lifecycle, deploy, monitor | config file, CLI, "add peer", "show tunnels" |

The test to tell control from management:

- Operator sets it up by hand → **management plane**.
- System decides it at runtime → **control plane**.

WireGuard is the cleanest real reference: the `wg` CLI + config is the management plane,
the Noise handshake + roaming is the control plane, the kernel crypto/forwarding is the
data plane.

## Architecture

```
        ┌────────────────────────────────┐
        │  orchestrator.py  (Python)     │   control + management plane
        │  read spec → gen config →      │   (your focus)
        │  docker run → wire → monitor   │
        └──────┬───────────────┬─────────┘
               │               │
          [Click #1]      [Click #2]      data plane (readable element graph)
```

- **Data plane**: Click, one Docker container per router.
- **Deployment**: Docker containers, one per router. Target Kubernetes in
  production; test locally with Minikube (or another local K8s).
- **Control plane**: Python logic for key exchange, route advertisement, reacting to events.
- **Management plane**: the spec (YAML), the CLI/config surface, provisioning, monitoring. Its only interface is the CLI — no GUI, no web dashboard.

In a small project the control and management planes live in the same Python program. The
boundary is the test above, not a file split.

## Project stages

1. **Static** — hand-write one Click config. Learn the element graph. This is the only
   mandatory low-level step, and it is small.
2. **Generator** — Python reads a YAML spec and emits the Click config. The mapping
   spec → config is the whole trick.
3. **N routers + wiring** — each chain element runs in its own container; the
   orchestrator builds the topology and wires it.
4. **Reactive loop** — change the spec → re-generate → re-deploy. This is the control loop.

## VPN stages

1. **GRE, no crypto** — control plane sets up a static tunnel; Click encapsulates. Learn
   the CP→DP push and tunnel mechanics.
2. **Add IPSec** — control plane exchanges keys and pushes them to Click's ESP elements.
   Now it is a real encrypted VPN.
3. **Add routes** — control plane tells each node "subnet X is behind peer Y". Now it is
   multi-site.

Architecture choice: start **centralized** (one Python controller that nodes register to),
move to a **per-node daemon** (WireGuard-style) later.

### The one trap

Do not hand-roll cryptography. Use pre-shared keys + a crypto library (or the Noise
framework) and let Click's IPSec elements do the actual encryption. The control plane's
real work is key and route exchange, not the cipher.

## Click elements (data plane)

- `FromDevice` / `ToDevice` — NIC I/O.
- `Classifier`, `IPClassifier`, `IPFilter` — match and route.
- `IPRewriter` — NAT / connection tracking.
- `Queue`, `SimpleQueue`, `RatedSource` — buffering and rate control.
- `Strip`, `Unstrip` — encapsulation / decapsulation.
- `IPEncap`, `GREEncap` — tunneling.
- `IPsecESPEncap`, `IPsecESPDecap`, `IPsecRouteTable` — VPN crypto and routing.
- `Discard` — drop.
- Later, for performance: `ToDPDKDevice`, `ScheduleInfo` (the DPDK / CPU-pinning path).

Caveat: Click's documentation is old and scattered. Start from the wiki's "Elements" list
and the `click --help` element reference, not tutorials. The config language itself is
stable and small.

## Spec → config example

```yaml
# spec (management plane: the network service)
chain:
  - classifier: tcp or udp
  - firewall:   drop port 23
  - queue:      rate 10Mbps
```

```click
// generated by the orchestrator (the deployed instance)
FromDevice(eth0)
  -> Classifier(12/0800)
  -> IPFilter(drop dst port 23)
  -> RatedSource -> Queue -> ToDevice(eth1)
```

The orchestrator writes the second file. That is the whole project.

## Glossary (key concepts)

- **NF** — Network Function: a network capability (firewall, router, AMF, UPF).
- **VNF** — Virtual Network Function: an NF packaged as software on a VM.
- **CNF** — Cloud-native Network Function: a VNF refactored into containers on Kubernetes.
- **NFV** — Network Function Virtualization: decoupling the function from the hardware.
- **MANO** — ETSI Management and Orchestration: NFVO (service) + VNFM (function) + VIM
  (infrastructure, e.g. OpenStack or Kubernetes).
- **SFC** — Service Function Chaining: linking multiple NFs in order for one traffic path.
- **NSD / VNFD** — descriptors: NSD = the chain (which VNFs + virtual links); VNFD = one
  VNF's spec. Packaged together in a CSAR and onboarded to the NFVO.
- **NST / NSI** — Network Slice Template (blueprint) vs Network Slice Instance (a running
  slice). One NST → many NSIs.
- **SST / SD / S-NSSAI** — 5G slice identifiers: SST = service type (1=eMBB, 2=uRLLC,
  3=mMTC, 4=V2X), SD = operator differentiator, S-NSSAI = SST + SD.
- **NSSF** — Network Slice Selection Function: picks the slice for a request.
- **AMF / SMF / UPF / AUSF / UDM / PCF / NRF** — 5G core microservices (see below).
- **RRU / DU / CU** — the disaggregated base station: Radio Unit (RF), Distributed Unit
  (real-time baseband), Centralized Unit (non-real-time). Basis of vRAN / RaaS.
- **SAGIN** — Space-Air-Ground Integrated Network: satellites + HAPS/drones + ground +
  (sea), 6G's 3D coverage.
- **Numerology** — OFDM parameter set, mainly subcarrier spacing (15 kHz × 2^μ). Wide =
  low latency, short range; narrow = high efficiency, long range. 6G picks per slice.
- **DPDK / SR-IOV / CPU pinning / hugepages / eBPF-XDP / Multus** — infra optimizations
  for line-rate packet processing and deterministic latency on K8s/VM/bare-metal.

### 5G core functions (one line each)

- **AMF** — access & mobility; device entry point, registration, handover.
- **SMF** — session management; creates PDU sessions, controls the UPF.
- **UPF** — user plane; forwards user packets, QoS, charging. The heavy one.
- **AUSF** — authentication against SIM credentials.
- **UDM** — subscriber database (4G's HSS).
- **PCF** — policy rules: QoS, charging, slice policy.
- **NRF** — service registry; NFs discover each other.
- Control plane: AMF, SMF, AUSF, UDM, PCF, NRF. Data plane: UPF.
